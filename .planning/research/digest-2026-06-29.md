### [2606.27122] Mostly Automatic Translation of Language Interpreters from C to Safe Rust (Reboot)
- **arXiv:** https://arxiv.org/abs/2606.27122
- **Submitted:** June 25, 2026 · cs.PL (cross-listed cs.SE)
- **Relevance:** 90% — code_translation
- **GitHub Issue:** [#1856](https://github.com/anchapin/portkit/issues/1856) — *Adopt Reboot Feature-Reduction Milestone Pipeline for Java-to-Bedrock Translation*

**Summary:** Reboot translates real-world C programs (6k-23k LOC) to safe Rust with only 1-11 human interventions. Two core ideas: (1) **Feature Reduction** — decomposes translation into a sequence of milestones, starting from the simplest version and incrementally restoring features, each milestone validated before proceeding; (2) **Multi-Agent Architecture** — orchestrates unreliable LLM coding agents through automated validation and feedback. Ablation confirms feature reduction improves translation by 6-20% over multi-agent alone. All translations pass 100% of provided test suites; 62-92% pass on unseen validation tests.

**PortKit applicability:** PortKit's primary failure mode is all-or-nothing translation of large complex mods. Feature-reduction milestone decomposition converts these into partial successes — translate simplest features first, validate at each step using tsc + Bedrock schema check (the contract-repair loop from #1268 becomes a per-milestone gate). The 6-20% improvement from decomposition alone is model-agnostic — pure pipeline restructuring, no model changes needed. For B2B, milestone checkpoints surface as a "guided conversion" tier where customers approve each feature batch before proceeding. Strong synergy with #1268, #1091, #1737, #1723, #1765.

### [2606.19725] Library-Aware Doubles and Iterative Repair for LLM-Generated Unit Tests in OpenSIL Firmware
- **arXiv:** https://arxiv.org/abs/2606.19725
- **Submitted:** June 18, 2026 (late-catch — first identified this sweep) · cs.SE
- **Relevance:** 80% — code_translation / code_llm_benchmarks
- **GitHub Issue:** [#1857](https://github.com/anchapin/portkit/issues/1857) — *Add Library-Aware Bedrock API Stubs and Compile-Dispatch Repair Loop for TypeScript Test Generation*

**Summary:** AMD paper presenting an automated unit-test authoring pipeline for constrained-dependency C firmware. Three contributions: (1) Library-aware doubles — auto-generates stubs/mocks/fakes for missing library symbols; (2) Iterative compile-dispatch repair loop driven by build log error classification; (3) Line-coverage-guided repair. Results: 73/76 functions compiled (96.1%), mean coverage 73.9% without guidance, 98.8% with coverage guidance.

**PortKit applicability:** Bedrock Scripting API TypeScript is structurally identical to the AMD firmware problem — @minecraft/server doesn't exist in standard Node.js test environments. Current PortKit has no automated unit test generation; converted mods require a live Minecraft server for any validation. Library-aware doubles = Bedrock API mock layer; iterative compile-dispatch repair extends #1268 with a coverage feedback dimension. Delivers CI-testable Bedrock output without live Minecraft — each converted mod ships with a test suite, directly supporting B2B trust.

### [2606.26979] How Much Static Structure Do Code Agents Need? A Study of Deterministic Anchoring
- **arXiv:** https://arxiv.org/abs/2606.26979
- **Submitted:** June 26, 2026 · cs.SE
- **Relevance:** 75% — ast_parsing / multi_agent_qa

**Summary:** Investigates whether lightweight static analysis (call graphs, inheritance hierarchies) can provide deterministic anchors for LLM agents — stable structural facts injected as plain-text comments that constrain probabilistic navigation. The "deterministic anchoring effect": static structure helps less by making agents smarter and more by making navigation disciplined and reproducible. Lightweight call/inheritance topology improves function-level localization (+2.2pp) and shortens trajectories (-1.6 interaction rounds). Scale-sensitive: optimal granularity depends on repo characteristics.

**PortKit horizon:** PortKit's LangGraph agents currently navigate the Java mod's class structure without injected structural anchors. Pre-injecting call graph topology (which Java class calls which, inheritance hierarchy) as plain-text context before each translation agent invocation could reduce stochastic failures and shorten translation trajectories. Low-cost experiment: measure whether injecting AST-extracted call graph summaries into PortKit's translator prompt reduces retry rate. Aligns with the deterministic AST post-processor approach from #1721.

### [2606.25514] Unlocking Model Potentials Through Adaptive Multi-Agent Scaffolding for Efficient Issue Resolution (icat-agent)
- **arXiv:** https://arxiv.org/abs/2606.25514
- **Submitted:** June 25, 2026 · cs.SE
- **Relevance:** 70% — multi_agent_qa

**Summary:** icat-agent replaces shared LLM context with synchronous event-based message passing across agents. Crucially, it uses a rubric-based issue quality check to strategically route: well-defined issues get parallel patching + validation; low-quality/ambiguous issues get preliminary exploration first. Outperforms SWE-agent, mini-SWE-agent, and Claude Code by 3.6-8.4% on SWE-bench Verified and 6.3-18.5% on SWE-bench Pro. $1.18/instance cheaper than multi-agent Claude Code baseline.

**PortKit horizon:** The rubric-based quality routing idea maps to PortKit's mod complexity tiers — a pre-translation quality classifier that routes simple mods through a lean pipeline (parallel translation+validation) and complex/ambiguous mods through a more expensive exploration path. Combines well with the feature-reduction milestone pipeline from #1856 (complex mods decomposed into milestones; simple mods translated in a single pass).

### [2606.17514] Unlocking LLM Code Correction with Iterative Feedback Loops
- **arXiv:** https://arxiv.org/abs/2606.17514
- **Submitted:** June 16, 2026 · cs.SE
- **Relevance:** 70% — code_translation

**Summary:** Systematic study of LLMs' ability to self-correct code through execution feedback (compiler errors + test case results). Key finding: reasoning models consistently improve over iterations, substantially outperforming non-reasoning models in leveraging feedback. Syntactic and runtime errors are tractable; logical/algorithmic failures are not. The iterative refinement framework converges for reasoning models where it stalls for non-reasoning models.

**PortKit horizon:** PortKit's contract-repair loop (#1268) would benefit from using reasoning models specifically for the repair iterations. The finding that logical/algorithmic failures don't improve through iterative feedback (even with reasoning models) reinforces the need for feature-level decomposition (#1856) — if a complex feature has a logic-level incompatibility with Bedrock, iterative repair won't fix it; decomposition makes that gap explicit and isolates it.
