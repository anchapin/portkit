## Paper Details

### 1. Ladder Logic Translation using Large Language Models in Industrial Automation
- **ArXiv**: https://arxiv.org/abs/2605.31458
- **Date**: May 31, 2026
- **Relevance**: 90%
- **Summary**: Presents an LLM-based approach to translating ladder logic programs between incompatible PLC vendor formalisms (Rockwell → Siemens). The paper provides a mathematical formulation of the vendor-translation problem covering: mismatched programming environments, incompatible constructs, semantic expressiveness differences between vendor formalisms, and black-box proprietary tooling. Addresses how to map constructs that have no direct equivalent in the target formalism.
- **PortKit Applicability**: Structurally isomorphic to PortKit's Java Forge/Fabric → Bedrock Scripting API translation problem. The PLC vendor-translation challenge maps directly: mismatched environments (Java+Forge API vs TypeScript+Bedrock Scripting API), incompatible constructs (Java event system → Bedrock events, Java block entities → Bedrock block components), and sparse proprietary documentation (Bedrock Scripting API). The mathematical formulation may provide a formal grounding for PortKit's conversion semantics and a principled approach to handling no-direct-equivalent constructs (currently handled ad-hoc).
- **Proposed Issue Title**: "Apply vendor-translation formalism from industrial PLC code translation to formalize Java→Bedrock construct mapping"

### 2. Knowledge Boundary Probing and Demand-Guided Intervention for LLM-Based Power System Code Generation
- **ArXiv**: https://arxiv.org/abs/2605.31478
- **Date**: May 31, 2026
- **Relevance**: 90%
- **Summary**: Shows that first-pass failures in power-system code generation are dominated by "API-knowledge boundary errors" — hallucinated function names, misused parameters, and mishandled result structures in versioned simulation libraries — not reasoning failures. Introduces a probing method to identify what API knowledge the LLM lacks, then a "demand-guided intervention" that injects the missing knowledge (from a structured API KB) at inference time rather than at training time.
- **PortKit Applicability**: Identical failure type to PortKit's Bedrock Scripting API hallucinations. The "API-knowledge boundary error" framing directly describes PortKit's top failure category (non-existent Bedrock methods, wrong parameter types, version-specific API changes). The demand-guided intervention approach — probe what the LLM knows about the Bedrock API, then inject missing knowledge into the prompt context — is complementary to the static AST+KB post-processor from last week (2601.19106): that paper catches hallucinations after generation; this paper prevents them before generation by identifying and filling knowledge gaps dynamically.
- **Proposed Issue Title**: "Add Bedrock API knowledge boundary probing + demand-guided context injection to prevent hallucinated API calls pre-generation"

### 3. What Breaks When LLMs Code? Characterizing Operational Safety Failures of Agentic Code Assistants
- **ArXiv**: https://arxiv.org/abs/2605.30777
- **Date**: May 29, 2026
- **Relevance**: 80%
- **Summary**: Incident-driven taxonomy of operational safety failures in autonomous coding agents during benign, goal-directed use. Failure categories include: environment breakage, fabricated success reports, silent data corruption, scope creep, irreversible side effects, and dependency mismanagement. Current benchmarks (pass@k, SWE-bench) do not capture these failure modes. The paper characterizes which agent architectures and tool-calling patterns are most susceptible to each failure type.
- **PortKit Applicability**: PortKit's converter and validator agents are subject to several of these failure categories: (1) "Fabricated success reports" — the validator reporting a conversion as correct when the Bedrock code contains runtime errors; (2) "Scope creep" — the converter modifying parts of the Java mod it shouldn't touch; (3) "Silent data corruption" — converted code runs but produces wrong behavior (a PortKit-specific concern when Bedrock event semantics differ from Java). This taxonomy should inform PortKit's QA pipeline audit (#1577) and the validator agent's failure classification logic.
- **Proposed Issue Title**: "Apply operational failure taxonomy to classify and harden PortKit's converter and validator agents against fabricated-success and scope-creep failures"

### 65–79% Relevance (Horizon Notes)

#### 4. Beyond pass@k: Redundancy-Aware RLVR for Multi-Sample Code Generation
- **ArXiv**: https://arxiv.org/abs/2605.28022
- **Date**: May 28, 2026
- **Relevance**: 75%
- **Summary**: Shows that correctness-only RLVR collapses sample diversity (multiple generation attempts converge on same solution). Proposes redundancy-aware RLVR objectives that balance correctness with implementation diversity. Uses JPlag (plagiarism detection) to measure implementation-level redundancy.
- **PortKit Horizon**: Relevant to MMSD fine-tuning (#1578). When PortKit eventually trains on conversion outputs using RLVR with test-passing as verifier, correctness-only reward will reduce the diversity of conversion strategies. This matters for handling the long tail of Java mods that require varied translation approaches. Phase 0.5b horizon.

#### 5. How Consistent Are LLM Agents? Measuring Behavioral Reproducibility in Multi-Step Tool-Calling Pipelines
- **ArXiv**: https://arxiv.org/abs/2605.28840
- **Date**: May 28, 2026
- **Relevance**: 70%
- **Summary**: Systematic empirical study of behavioral consistency in multi-step tool-calling agents — whether the same agent produces the same output on repeated runs. Characterizes non-determinism sources and their impact on downstream tasks.
- **PortKit Horizon**: PortKit's LangGraph pipeline non-determinism (different conversion outputs for the same mod on repeat runs) is a quality concern for reproducibility in user-facing deployments. Relevant to Phase 0.7 production hardening.
