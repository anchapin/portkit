### Paper Details

#### 1. Detecting and Correcting Hallucinations in LLM-Generated Code via Deterministic AST Analysis
- **ArXiv**: https://arxiv.org/abs/2601.19106
- **Date**: January 27, 2026
- **Relevance**: 85%
- **Summary**: Post-processing framework parses LLM-generated code into AST and validates every API call against a KB built from library introspection. Targets Knowledge Conflicting Hallucinations (KCHs): non-existent methods, wrong parameter names, wrong arities. 100% precision, 87.6% recall (0.934 F1), 77% auto-correction rate — all without re-invoking the LLM. Deterministic, non-executing, sub-second latency.
- **PortKit Applicability**: PortKit generates Bedrock Scripting API code where hallucinated method names and wrong API calls are a top failure category. Building a KB from `@minecraft/server` TypeScript type definitions + AST validation could catch these pre-execution, complementing runtime testing and cleaning the MMSD fine-tuning reward signal.
- **Proposed Issue Title**: "Add deterministic AST + Bedrock API KB post-processor to catch hallucinated API calls in converted code"

#### 2. Same Signal, Different Semantics: A Cross-Framework Behavioral Analysis of Software Engineering Agents
- **ArXiv**: https://arxiv.org/abs/2605.18332
- **Date**: May 18, 2026
- **Relevance**: 80%
- **Summary**: 64,380 SWE-bench runs across 126 configurations / 43 frameworks. Framework identity explains 64% of behavioral variance; LLM family explains only 10%. Behavioral signals (e.g., "lower error rate → better resolution") reverse direction across frameworks — 47 vs 48 configurations for error rate alone. Single-framework behavioral findings should not be claimed as general rules.
- **PortKit Applicability**: Validates that PortKit's investment in LangGraph-specific pipeline tuning matters more than LLM selection. Also warns that behavioral rules from SWE-Agent/OpenHands literature shouldn't be naively applied to PortKit's LangGraph pipeline without validation. Directly relevant to how the team interprets evaluation data and prioritizes optimization effort.
- **Proposed Issue Title**: "Validate PortKit's LangGraph behavioral assumptions against cross-framework SE agent evidence"

### 65–79% Relevance (Horizon Notes)

#### 3. AstraAI: LLMs, Retrieval, and AST-Guided Assistance for HPC Codebases
- **ArXiv**: https://arxiv.org/abs/2603.27423
- **Date**: March 28, 2026
- **Relevance**: 75%
- **Summary**: CLI framework for HPC code generation combining LLMs, RAG from codebase, and AST structural analysis. Constructs high-fidelity prompts with relevant code snippets + structural context. Performs scoped modifications while preserving structural consistency. Supports local and API-hosted models.
- **PortKit Horizon**: AstraAI's "RAG + AST context for scoped modifications preserving structure" is architecturally similar to PortKit's Java AST parser + Bedrock API RAG (→ #1189). Validating whether AstraAI's prompt construction strategy improves PortKit's converter quality could be a Phase 0.6 experiment.

#### 4. Reinforced Graph of Thoughts: RL-Driven Adaptive Prompting for LLMs
- **ArXiv**: https://arxiv.org/abs/2605.22195
- **Date**: May 21, 2026
- **Relevance**: 70%
- **Summary**: Automates Graph of Thoughts prompting using RL to adaptively generate the graph of operations from a human-defined set. Under certain constraints, constructs graphs adaptively to task complexity.
- **PortKit Horizon**: PortKit's LangGraph pipeline is a graph of operations (parse → plan → convert → validate → repair). Making that graph adaptive to mod complexity — e.g., routing simple mods through fewer nodes vs complex mods through extended repair loops — could improve throughput for the 60-80% "easy" conversions while preserving quality on the hard ones.

#### 5. Can LLMs Produce Better Object-Oriented Designs than Human-Involved Development?
- **ArXiv**: https://arxiv.org/abs/2605.19901
- **Date**: May 19, 2026
- **Relevance**: 65%
- **Summary**: Comparative study (Java assignments): PureAI projects show lower code smell density but tend toward oversimplification — missing abstractions, weaker responsibility separation. Human guidance on OOP decomposition remains important even when LLMs are used.
- **PortKit Horizon**: When PortKit converts complex Java mods with rich OOP hierarchies (event handlers, block entities, capability providers), the converter may over-simplify the generated Bedrock Scripting API code — flattening abstractions that should be preserved for maintainability. Product-level concern rather than immediate technical action.
